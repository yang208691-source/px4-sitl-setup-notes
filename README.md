## 两条最有价值的内容

### 1. Gazebo topic 三层诊断法

```bash
gz topic -l                          # ① 列：有哪些 topic
gz topic -i -t <topic>               # ② 看：谁在发、谁在收
gz topic -e -t <topic> > /tmp/o.txt  # ③ 抓：必须文件重定向
```

> ⚠️ 第 ③ 步**不能用管道**（`| head`）—— 管道是块缓冲的，小消息可能填不满缓冲区就被 timeout 掐掉，让你误判成"没数据"。我在排查中差点被这个骗过去。

**这套方法可以套用到任何 gz-transport 链路问题**，不限于 PX4。

### 2. 用 `*_groundtruth` 一刀切开"飞控的问题"还是"物理的问题"

PX4 SITL 的 ulog 里有 `vehicle_local_position_groundtruth`、`vehicle_attitude_groundtruth` —— **这是仿真世界里的真相，不受估计器和控制器干扰。**

有它就能立刻判断：是飞控算错了，还是物理世界根本没动。**这个判断直接决定你往哪个方向查，真机排故时同样适用。**

## 关键结论

> ### ⚠️ 不要用 PX4 `main` 分支开发版做开发

实测 `v1.18.0-beta1-700`（main 分支）的 `gz_bridge` **不向 Gazebo 发布电机指令** —— 载具在仿真里完全不动，而且**不报任何错、不打任何日志**。

同一测试在两个版本下的结果：

| PX4 版本 | `gz topic -e` 抓 10 秒 |
|---|---|
| `v1.18.0-beta1-700`（main） | **0 字节** ❌ |
| `v1.15.4`（稳定版） | **119,560 字节** ✅ |

**换稳定版立即恢复正常。**
