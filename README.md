## 五条最有价值的内容

### 1. Gazebo topic 三层诊断法（setup-log）

```bash
gz topic -l                          # ① 列：有哪些 topic
gz topic -i -t <topic>               # ② 看：谁在发、谁在收
gz topic -e -t <topic> > /tmp/o.txt  # ③ 抓：必须文件重定向
```

> ⚠️ 第 ③ 步**不能用管道**（`| head`）—— 管道是块缓冲的，小消息可能填不满缓冲区就被 timeout 掐掉，让你误判成"没数据"。我在排查中差点被这个骗过去。

**这套方法可以套用到任何 gz-transport 链路问题**，不限于 PX4。

### 2. 用 `*_groundtruth` 一刀切开"飞控的问题"还是"物理的问题"（setup-log）

PX4 SITL 的 ulog 里有 `vehicle_local_position_groundtruth`、`vehicle_attitude_groundtruth` —— **这是仿真世界里的真相，不受估计器和控制器干扰。**

有它就能立刻判断：是飞控算错了，还是物理世界根本没动。**这个判断直接决定你往哪个方向查，真机排故时同样适用。**

### 3. PX4 控制链路的频率地图（devlog-01）

```
50 Hz    trajectory_setpoint      轨迹层
125 Hz   mc_pos_control           位置环   → vehicle_attitude_setpoint
250 Hz   mc_att_control           姿态环   → vehicle_rates_setpoint
250 Hz   mc_rate_control          角速率环 → vehicle_torque_setpoint
250 Hz   control_allocator        混控     → actuator_motors
```

**内环必须比外环快 2–5 倍** —— 外环的输出是内环的输入，内环不够快，外环的指令还没执行完就被新指令覆盖。

**不知道谁在多少 Hz 上跑，就看不懂控制器为什么那么设计。**

### 4. 用独立数据源交叉验证结论（devlog-01）

日志里 Yaw 在 5s 处从 0 跳到 90°。两种可能：

| 假设 | 验证方法 | 结果 |
|---|---|---|
| 飞机真的转了 90°？ | 看真实陀螺仪 `vehicle_angular_velocity` 的 yaw rate | 该时刻为 **0** ❌ 排除 |
| EKF 估计器复位？ | 姿态跳变但陀螺仪无响应 | ✅ **成立** |

**一个现象、两条独立数据、互相印证。**

> 反面教材：用 `np.diff(yaw)/dt` 从四元数**差分**估算角速率，在跳变点算出了 >20000 deg/s 的假尖峰。
> **永远不要用姿态差分反推角速率** —— 飞控里本来就有真实测得的角速率。

### 5. 看到"陡变"，先算三个数（devlog-02）

```
① 这个变化用了多长时间？      ← 从数据算，不是从图看
② 这个变化率物理上可能吗？    ← 对比物理上限，如 a ≤ g·tan(θ_max)
③ 图的时间尺度是多少？        ← 1 秒在图上占几个像素？
```

**一次任务飞行日志里，水平速度看起来在 0 和 5 m/s 之间"垂直跳变"。**

排查过程：

1. **记录层有问题吗？** → 时间戳间隔 99.99% 是 8000 us → 排除
2. **速度估计有问题吗？** → 最大加速度 4.1 m/s²（物理上限约 3.2 m/s²，同量级）→ 排除
3. **放大 20 秒窗口** → **平滑的 S 形加速曲线**

**真因：1.2 秒的加速过程，在 732 秒的图上不到 1 个像素。**

> **数据从来没错，是看图的人错了。** 任何长时间跨度的图都会骗你 —— **立成纪律，不靠记性**。

## 关键结论

### ⚠️ 不要用 PX4 `main` 分支开发版做开发

实测 `v1.18.0-beta1-700`（main 分支）的 `gz_bridge` **不向 Gazebo 发布电机指令** —— 载具在仿真里完全不动，而且**不报任何错、不打任何日志**。

同一测试在两个版本下的结果：

| PX4 版本 | `gz topic -e` 抓 10 秒 |
|---|---|
| `v1.18.0-beta1-700`（main） | **0 字节** ❌ |
| `v1.15.4`（稳定版） | **119,560 字节** ✅ |

**换稳定版立即恢复正常。**

### ⚠️ SITL 和真机是两套环境

| | SITL / POSIX | 真机 / NuttX |
|---|---|---|
| 本质 | Linux 多线程进程 | RTOS 独立任务 |
| 系统命令 | `top` / `htop` / `gdb` | `top` / `free` / `ps` |
| 任务间内存 | 共享地址空间，越界不会立刻崩 | 独立栈，**栈溢出直接死机** |
| 时序 | 不严格（仿真） | **硬实时**，超时即故障 |

**SITL 上学到的命令，上真机前要重新确认一遍** —— 反着也会踩坑。

### ⚠️ PX4 里所有 `timestamp` 都是 `uint64`

**任何时间戳相减之前，先显式转成有符号类型。** 无符号回绕不报错，只会给你一个看似合理的巨大数字（详见 devlog-01 坑 5）。

### ⚠️ 容量值必须带单位（`.wslconfig`）

裸数字按**字节**解析 —— `memory=12288` 会被当成 12 KB（详见 setup-log 坑 3）。

## 一句话总结

> 环境搭建的坑 **90% 在网络和构建系统，不在飞控本身**。
> 二次开发的第一步 **不是改控制律，是建立可观测的闭环** —— 没有观测，改任何参数都是盲调。
>
> 贯穿两者的纪律：**先观测，后动手；要对照，看数据；标注可信度。**
